The experiment: the only change was `netChangePerAccount` using a `LinkedHashMap` instead of the sorted `TreeMap`, so `lockBalances` locked accounts in the order the lines arrived. The failures in the last run were PostgreSQL `ERROR: deadlock detected` on `select balance from balances where account_id = ? for update` (for example "Process 80 waits for ShareLock on transaction 847; blocked by process 82. Process 82 waits for ShareLock on transaction 849; blocked by process 80"), plus `CannotCreateTransactionException: Could not open JDBC Connection`. Why: with 10 accounts and 50 threads, one transfer A to B and another B to A each lock their first account and then wait for the other's, and neither can proceed. PostgreSQL breaks each cycle by aborting one transaction. The connection errors are most likely a side effect (aborted and waiting transactions hold pooled connections while the pool of 10 has a 2000 ms timeout); I did not verify that separately. With sorted locking the same test passed 40 of 40 runs. The experiment branch is local only, one commit, and was not merged or pushed.

The knee is at 10 VUs, the pool size. Up to 10, every request has a connection and p95 stays under 10 ms. Past it, throughput stops rising (1,524 at 10 VUs, 1,503 at 25) and every extra VU waits for a connection, so p95 grows with the queue: 24.9 ms at 25 VUs, 229.4 ms at 200. At the knee the pool is full, but on average only 2.4 of its sessions are running a statement in PostgreSQL while 6.3 are idle in transaction: the transaction is open and the app is between statements, on a round trip. Lock waits are 0.0, PostgreSQL uses about 1.5 of the VM's 5 CPUs, and the host is at 75%. So a posting holds its connection mostly for round trips, which is what the one change below shortens. The 50-VU step is below the 25 and 100 steps because posting slowed for about 80 s in its middle (01:13:57 to 01:15:17 UTC): the outbox grew 295 to 822 rows a second instead of 891 to 1,315 before it, host CPU rose to 83 to 94% and the app's own CPU fell from 13 or 14% to 7 to 11%. The samples do not show what else used the host.

Hot account, in plain words: every transfer in scenario B pays account 1, so every posting has to lock account 1's balance row and keep it until it commits. Only one posting can hold that lock at a time, so the postings form a single queue, and B's throughput is one posting per lock hold, whatever the number of users, connections or cores. The samples show it: in the final B run about 7.8 of the 8.0 active database sessions were waiting on a lock, the pool was full with 32 requests waiting for a connection, and PostgreSQL used about 36% of one core against about 141% in the final A run. B runs at about a third of A's rate on the same machine. Shorter lock holds help a little (B's median rose from 522 to 607 req/s with the change, on the B runs above that started on A's backlog), but only spreading the hot account's balance over several rows, which this ledger does not do, would lift the ceiling itself.

## Open decisions (review before the project ends)

- Log lines in Grafana (from Phase 5, 2026-10-26). This is the unmet part of PLAN.md's Phase 5 Verify ("tell me exactly where in Grafana to find ... its log lines by entry id"), not a nice-to-have. Today log lines are JSON on the console only, with `traceId`, `spanId`, `entry_id` and `idempotency_key`, and are not sent to Loki. The OpenTelemetry Logback appender was removed because it is alpha. The preferred way back, option A: a small Logback appender of our own in `common` on the stable logs API `io.opentelemetry.api.logs` (in `opentelemetry-api` 1.62.0, managed by Spring Boot, already on the classpath), handing each line to Spring Boot's OTLP log exporter, with an integration test that finds a line in the test container's Loki by entry id. No new dependency or container. Option A must also remove `management.logging.export.otlp.enabled: false` from `application.yaml`, which switches that exporter off today. Options considered and not preferred: Spring Boot file logging read by the collector inside otel-lgtm (its `file_log` receiver, module filelogreceiver, is Beta for logs in the image's otelcol-contrib 0.162.0, both read from `otelcol-contrib components` and `--version` in grafana/otel-lgtm:0.37.0); a Grafana Alloy container tailing a log file (a new image and more moving parts); the OpenTelemetry Java agent (an unlisted download that changes how the app starts).

- The risk cap (100) and keep-alive (4 s) were not measured under load. A load run with the risk engine on would show whether 100 calls in flight is enough.

If idempotency-key expiry (a stretch item) ever deletes keys, a key deleted between that check and the claim would post without asking the risk engine.
