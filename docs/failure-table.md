# Failure table

Each failure test runs the app against PostgreSQL and Kafka behind Toxiproxy 2.13.0 (`FailureTest`). After every test the links are restored and four checks run over connections straight to the containers: total money per currency unchanged, every balance equal to the sum of its lines, each idempotency key with at most one entry, and a Kafka consumer that saw every entry, keeping one copy of each.

Runs from 2026-10-27 on a Mac (darwin arm64), Java 25.0.1, Docker 29.9.2, postgres:18.6, apache/kafka:4.3.1. "What failed first" is the first run of each scenario; the fix column links the commit that changed production code.

Notes

- PLAN.md cuts a link with a bandwidth of 0 both ways. Toxiproxy 2.13.0 reads a bandwidth of 0 as no limit (its #764), so that cut would have let every byte through and the tests would have passed without testing anything. The tests use a timeout toxic of 0 both ways instead, which drops every byte; removing it closes the connections it held. Each test also asserts that its fault reached the app.
- A database cut can make Kafka see an entry twice. In one run of `DbConnectionDropIT`, Kafka acknowledged a relay batch and then the relay's `update outbox set published_at` failed on the cut link, so the batch rolled back and was sent again after the restore: 17 entries arrived twice and the consumer kept one copy of each. Delivery is at least once by design (docs/design.md).
- A 503 for a slow database still took 4.2 to 6.2 s with a 1 s transaction timeout. Spring checks the deadline before each statement, so a statement already on the 2 s round trip runs to its end, and the rollback is one more round trip. That explanation is my reading of Spring's per-statement deadline; it was not measured separately.
